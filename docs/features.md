# Features and their status

For people who need to know what is ready. [The README](../README.md) has the short table (feature and status); this page
has the notes and the evidence behind each row. Facts about third parties are marked *verified* with a date, or are
unverified.

Legend: ✅ built and tested in CI · ⚠️ built, but partial or not yet proven end to end · 🚧 being built ·
📋 planned · ⏸️ on hold · ❌ not built or not done. Updated with every change that moves a row.

## Features

| Storage | PostgreSQL 19 or later, the only infrastructure | ✅ | Older servers are refused at connect |
| Intake | Usage events accepted once by id; a replay changes nothing | ✅ | One `ON CONFLICT DO SELECT` statement; a differing payload is a conflict ([ADR 0001](adr/0001-postgres-is-the-queue.md)) |
| Intake | Partitioned queue by occurrence day, made ahead of time | ✅ | `ob_prepare_partitions` |
| Intake | Dropping old partitions after the window plus a margin | ⚠️ | `retention.margin`, default 90 days (the owner's decision of 2026-11-28); `ob_expired_partitions` and `ob_drop_partition`, the detach run as a top-level `DETACH … CONCURRENTLY` by `openbilling serve` under an advisory lock, once at start and then hourly. Proven on PostgreSQL 19.0, never on a real deployment ([ADR 0001](adr/0001-postgres-is-the-queue.md), G1 to G5) |
| Intake | Pre-priced events (each carries its amount) | ✅ | |
| Intake | Raw events rated at intake | ✅ | A meter, a quantity and dimensions; the event and its outcome keep their price version ([ADR 0004](adr/0004-a-versioned-price-book-in-sql.md)). Through the API: `recordRawUsage`; the price list: `loadPriceList` |
| Queue | Drain with `FOR UPDATE SKIP LOCKED`, once-only per event | ✅ | Concurrency tested on the conformance suite |
| Queue | Workers woken by `LISTEN/NOTIFY`, the table as the truth | ✅ | |
| Queue | A worker loop in the service binary | ⚠️ | `openbilling serve` drains on `LISTEN/NOTIFY` with a 5 s poll and prepares partitions hourly; three at once on one database in the end-to-end suite, run by CI's Test job on PostgreSQL 19.0; never on a real deployment |
| Rating | A versioned price book, loaded from YAML, rated in SQL | ✅ | Loaded once per content, never changed or back-dated; each event priced by the version in force when it happened, half to even once per event; unpriced meters and dimensions refused ([ADR 0004](adr/0004-a-versioned-price-book-in-sql.md)) |
| Accounts | An owner holds several accounts (one per currency and label) | ✅ | [ADR 0002](adr/0002-an-owner-holds-several-accounts.md) |
| Ledger | Double-entry, append-only, amounts in integer micro-units | ✅ | Every transaction balances, enforced by triggers |
| Ledger | Configurable draw order across accounts and lots | ✅ | |
| Ledger | Debt, a debt limit, and repayment from new credit | ✅ | Usage is always booked, as debt past the limit (the owner's decision of 2026-11-27, "Always book as debt"); the limit refuses new calls through `allowed` (`debt_limit`, compared as the deployer's configuration says) and flags the owner (`pastLimit`, debt above the limit, on the balance read and on `allowed`) |
| Ledger | Monthly allowance, granted once per account and month | ✅ | |
| Credits | Sources: payment, promotion, adjustment, each once-only by id | ✅ | |
| Credits | Refunds and chargebacks, capped at the payment | ✅ | Enforced by a trigger, also under concurrency |
| Budget | `allowed`: may this owner spend, with per-member monthly caps | ✅ | Three checks in order, the debt limit, the balance (the debt against the drawable credit) and the member's cap, each a plain comparison with no special case for zero (the owner's decision of 2026-11-27: "Its not the role of this service to judge that") |
| Budget | The deployer chooses how `allowed` compares, in YAML | ✅ | `OPENBILLING_CONFIG` names one optional file: `allowed.debt_limit`, `balance` and `member_cap`, each `at_or_above` (the default), `above` or `never` (report only). An unknown key or value is refused at start; the rule stays in SQL, the mode passed in ([ADR 0001](adr/0001-postgres-is-the-queue.md), amended, F1 to F4). The chart's `openbilling.config` renders it |
| Budget | `allowed` reports its numbers, whatever the verdict | ✅ | The net balance, the drawable credit, the debt, the limit, `pastLimit`, the member's usage this month, their cap and what is left: a caller with its own rule reads them and ignores the verdict |
| Reads | Balance, lots, event outcomes, usage per day | ✅ | SQL functions today; an outcome is a plain query since slice 3; through the API as CrateStack models and `query` blocks (below) |
| Reads | Monthly statements | ✅ | A CrateStack `query` block: usage per day and meter, credits, reversals, allowances, a total per kind. Run in CI on PostgreSQL 19 |
| Payments | A payment-provider port with vpay as the first adapter | ⚠️ | Signed webhooks become once-only credits; top-ups through the provider; each payment read back before it is credited ([ADR 0003](adr/0003-credits-from-a-payment-provider.md)). The port's suite runs against a vpay stand-in; never against a real vpay (`vpay-sandbox.yml`, manual, has never run). The adapter mints its own `vpay:v1` token (`client_credentials` with an RS256 `private_key_jwt`, ADR 0003 amended 2026-11-28), proven against the stand-in only |
| Payments | Top-ups recorded, a changed payment refused, pending top-ups read back on a timer | ⚠️ | Each top-up is recorded when it starts and a payment read back is compared with it in SQL: a changed owner, label, currency or amount credits nothing and stays refused (`payments.unrecorded`, default `refuse`, decides a payment with no record). `serve` reads pending top-ups back on a timer (`reconcile`), once more at `stop_after` before one expires. Proven against the stand-in, which can change a payment after it was asked for; vpay has not been asked (ADR 0003 amended 2026-11-28, ANR-1405 and ANR-1473) |
| Payments | An operator resolves a mismatched top-up, once | ⚠️ | `resolveTopUp(payment, outcome)`, allowed to the `operator` role (mapped from the issuer's claim by `OPENBILLING_AUTH_ROLE_MAP`): `credit_recorded` credits the recorded terms and needs a payment the provider reports as succeeded; `dismiss` closes it with no credit; both final, two operators at once credit once, the operator's subject is kept for audit and in no log, metric or answer. A mismatch no top-up was recorded for can only be dismissed. Proven against the stand-in only; no written runbook yet (ADR 0003 amended 2026-11-28, ANR-1474, PR #38) |
| API | External API through CrateStack: on-demand queries, custom selects, policies | ✅ | Models over the ledger's tables, `query` blocks behind read procedures, mutation procedures that call the SQL functions, an `Idempotency-Key` on every write; the contract lock and `docs/api/ops.json` checked in CI. Its flow tests run in CI on PostgreSQL 19 |
| API | A Rust SDK, `openbilling-sdk`: typed calls for every operation, generated by CrateStack from the schema | ⚠️ | `crates/openbilling-sdk`: the generated client (`include_client_schema!`) with a thin facade (base URL, bearer token, a required `IdempotencyKey` on every write, errors with a class that never hold the token); its schema copy is held equal to the server's by a test and CI; `e2e/sdk.rs` drives the real service with it. **Not yet published to crates.io**: `cargo publish --dry-run` runs on every pull request, the first release is the owner's, by hand, and `release.yml`'s `publish-sdk` job (trusted publishing) takes over after it ([ADR 0008](adr/0008-a-rust-sdk-on-crates-io.md)) |
| API | Authentication of API callers, fail-closed | ✅ | A bearer `AuthProvider` over a `TokenVerifier` port: no token, or one refused, is a `401`. `openbilling-jwt` verifies a JWT against one issuer's JWKS (`RS256`, `ES256`, `EdDSA` only; `iss` and `aud` exact; `exp` required; roles from a configured claim), signatures on ring; with no issuer configured every call is refused. Never tried against a real identity provider, only a test issuer |
| Testing | A conformance suite for every `LedgerStore` | ✅ | |

Run by CI's Test job, a step of its own, against the PostgreSQL 19.0 service CI pins; the real service is never tried against a real identity provider or vpay |
| Command line | `openbilling serve`, `--help`, `--version`, with clap and colour | ⚠️ | Colour off when not a terminal, `NO_COLOR` and `CLICOLOR_FORCE` honoured (tested); the help and the colour are tested; `serve` is what the end-to-end suite runs |

## Ready for production?

What is proven so far is proven on one machine or one CI runner, against stand-ins and test issuers. These rows are
what is **not** proven anywhere real. The README's short table repeats them.

| Question | Status | Where it stands |
|---|---|---|
| Deployed on a real cluster | ❌ | Not yet. The published chart installs in a kind cluster against PostgreSQL 19.0 (`release-check.yml`, 0.4.0 and 0.5.0) and the service answers `/readyz`; nothing has run it in a cluster that carries real traffic, a real database service or a real ingress. The chart's `PrometheusRule` and dashboards ConfigMap are rendered, never applied to a cluster |
| A real payment provider (vpay) | ❌ | `vpay-sandbox.yml` (manual, three conformance cases against a vpay sandbox) has never run. Everything on the payment path (webhooks, the token, top-ups, the read-back and its refusal, reconciliation, a resolution) is proven against the vpay stand-in only, and the stand-in is written by us |
| A real identity provider | ❌ | Only `openbilling-jwt`'s test issuer on a loopback port has signed a token the service accepted. The verifier is tested against one issuer's JWKS, with `RS256`, `ES256` and `EdDSA`; no external issuer has been tried, nor key rotation against one |
| An operator procedure for payment mismatches | ⚠️ | The mechanism exists: `resolveTopUp` (see the Payments rows above), counted in `openbilling.topups.resolved` and `openbilling.payments.mismatches`, with an alert and panels (their README lines still say "settle it by hand", from before `resolveTopUp`). No written runbook says how an operator finds a mismatch, what to check at the provider before choosing `credit_recorded` or `dismiss`, or who holds the `operator` role |
| Alert routing and paging | ❌ | The rules fire and resolve against a real Alertmanager on a runner. No receiver, route or on-call integration is shipped |
| Backups and restore of the database | ❌ | Nothing in this repository takes, tests or documents them |
| Load and capacity | ⚠️ | The end-to-end suite drives 10 000 events over three services on PostgreSQL 19.0; no benchmark or sizing guide exists |
